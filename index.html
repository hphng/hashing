Stage 01 · Separate chaining · Beginner
Chaining with linked lists
The original hash table. An array of N slots where each slot holds a pointer to a linked list of nodes. When two keys hash to the same slot, they coexist in the same chain. Simple, flexible, and the mental model every other strategy builds on.
introduction

Hash tables were invented around 1953 independently by Hans Peter Luhn at IBM and Gene Amdahl. The linked list variant became dominant because dynamic memory allocation made it natural — each chain can grow indefinitely without preallocating space.

The core idea is simple: turn a key into a number using a hash function, use that number as an array index, and store the value there. When two keys produce the same index (a collision), just append to the chain at that slot.

Unix's original ndbm database (late 1970s) used separate chaining. It became the mental model for a generation of systems programmers and is still the first hash table taught in every CS curriculum worldwide.

how collision handling works

When insert("alice", 1) and insert("bob", 1) both hash to slot 3, the slot holds a chain: alice → bob → nullptr. Lookup walks the chain comparing keys until it finds a match or hits nullptr.

Key insight: the chain can grow as long as needed. You never run out of space the way open addressing does. This is the main advantage over stages 3–5.

Deletion is clean — just pointer surgery. Find the node, update the previous node's next pointer to skip it, then delete. No tombstones, no side effects. This is why some production systems prefer chaining even when open addressing is faster on average.

load factor

Load factor = n items / k slots. This equals the average chain length. At load factor 0.75, you walk ~1.5 nodes per lookup on average. At 2.0, you walk ~2.5 nodes. The standard threshold is 0.75 — this number is literally hardcoded in Java's HashMap source.

Why 0.75 specifically? It comes from a mathematical tradeoff — at 0.75, expected comparisons per lookup is ~1.5 while memory waste is acceptable. At 1.0 it jumps to ~2.5. The number 0.75 is not arbitrary.

The worst case is not just theoretical. In 2011, a HashDoS attack exploited predictable hash functions to craft keys that all land in the same bucket, turning O(1) lookups into O(n) and crashing PHP, Python, and Ruby servers. The fix: randomize the hash seed per-process, which Python, Ruby, and Java now do by default.

who uses it & where
Java HashMap
Uses linked list chaining. Since Java 8, converts chains longer than 8 nodes to red-black trees → O(log n) worst case instead of O(n).
C++ std::unordered_map
Standard library hash map uses separate chaining. Known for poor cache performance due to pointer chasing — why alternatives like absl::flat_hash_map exist.
Redis (internally)
Uses a custom chained hash table (dict.c) with two tables for incremental rehashing — avoids the latency spike of rehashing all at once.
CPython dict (old)
Early Python dict used chaining before switching to open addressing in Python 3.6 for memory and cache efficiency.
things most people don't know

Prepend, don't append. Most implementations prepend new nodes to the head of the chain instead of appending to the tail. This avoids walking to the end every time and is O(1). The order of nodes in a bucket doesn't matter for correctness.

Redis uses two tables at once. When Redis resizes, it keeps both the old and new table active simultaneously, moving a few buckets per operation. This spreads the O(n) rehash cost across many requests instead of one giant pause — critical for a low-latency server.

Java 8's tree conversion is controversial. Converting buckets to red-black trees adds complexity and only helps in adversarial (HashDoS) scenarios. Under normal loads with a good hash function, the linked list never gets long enough to matter.

Stage 02 · Separate chaining · Beginner
Chaining with dynamic arrays
Same strategy as stage 1 — but instead of a linked list per bucket, use a std::vector. The hash table logic is identical. The difference is purely in memory layout, and that difference has a measurable impact on real-world performance.
introduction

Linked lists have one fundamental problem: every node is a separate heap allocation at a random memory address. To walk a chain of 5 nodes, your CPU makes 5 round trips to different memory locations. Each trip that isn't in cache costs ~100 CPU cycles. This is called a cache miss.

Dynamic arrays (vectors) store all elements contiguously in memory. When you access the first element, the CPU automatically loads the surrounding memory into cache. Accessing the second element is then nearly free — it's already in cache. This is called spatial locality.

how collision handling works

When two keys land in the same bucket, they're stored as consecutive entries in the same std::vector. Lookup iterates through the vector's elements linearly — but since they're contiguous in memory, this linear scan is extremely fast in practice.

Trade-off: deletion in a vector requires shifting elements or swapping with the last element. Linked list deletion is cleaner (pointer surgery). If your workload is deletion-heavy, linked list chaining may be preferable.

load factor

Same rule as stage 1 — keep load factor below 0.75. The difference is that at the same load factor, dynamic array chaining is faster because the CPU can prefetch the entire bucket into cache in one operation.

Google's internal hash map (later open-sourced as part of sparsehash) used contiguous storage to maximize cache efficiency.

things most people don't know

The swap-with-last trick. To delete from a vector without shifting all elements, swap the target element with the last element, then pop the last. O(1) deletion — but it changes the order of elements in the bucket. For a hash map this is fine since order doesn't matter.

Vector overhead. Each std::vector is 24 bytes (pointer + size + capacity) even when empty. With 1 million buckets, that's 24MB of overhead just for empty buckets. For sparse tables, this is worse than linked lists which use 8 bytes (one null pointer) per empty slot.

Stage 03 · Open addressing · Easy–Medium
Linear probing
No pointers. No separate chains. One flat array holds everything. When a slot is occupied, try the next one. Then the next. This simplicity makes it the most cache-friendly hash table design — and the one used inside Python's dict.
introduction

Open addressing was developed in the 1950s alongside separate chaining. The key insight: if the hash table array itself is the only memory you use, cache performance is dramatically better. No pointer chasing, no heap allocations per element — just sequential memory access.

Linear probing is the simplest open addressing scheme: when slot h(k) is full, try h(k)+1, h(k)+2, etc., wrapping around. The probe sequence is just incrementing the index.

collision handling & the clustering problem

When two keys land at the same slot, the second one probes forward until it finds an empty slot. This works — but creates primary clustering: once a run of filled slots forms, every new collision that lands anywhere in that run makes the run longer. Clusters grow superlinearly.

Tombstone deletion. You cannot simply empty a slot when deleting — it would break the probe chain for elements that probed past it. Instead, mark the slot as "deleted" (tombstone). On lookup, keep probing through tombstones. On insert, reuse tombstone slots. Without tombstones, deletion corrupts the table.

load factor

Keep load factor below 0.7 — stricter than chaining. At 0.9 load factor, average probes per lookup explodes to ~5.5. At 1.0 the table is full and insert loops forever. Tombstones also count toward load factor and must be tracked.

time & space complexity
operationaverageworst casenote
insertO(1)O(n)clustering causes long probe sequences
lookupO(1)O(n)must probe through entire cluster
deleteO(1)O(n)tombstone required — can't just empty slot
spaceO(n)O(n)no per-element pointer overhead
who uses it & where
Python dict
CPython's dict uses open addressing with a custom probe sequence (not pure linear). Python 3.6+ made dicts ordered by insertion as a side effect of the implementation.
PHP arrays
PHP's array type (which is an ordered hash map) uses open addressing internally, making it one of the most-used hash table implementations in the world.
V8 (JavaScript)
Google's JS engine uses open addressing for object property lookup — critical path for all JavaScript execution.
things most people don't know

Linear probing beats quadratic probing in practice. Despite causing more clustering, linear probing's sequential memory access pattern is so cache-friendly that it often outperforms quadratic probing on real hardware, even with more collisions.

Tombstone accumulation. A table with many deletions fills up with tombstones that slow down both lookup (must probe through them) and insert (must scan past them). Periodic rehashing clears tombstones — this is why some implementations rehash even when the element count hasn't grown.

Stage 04 · Open addressing · Easy–Medium
Quadratic probing
Same flat array as linear probing, but the probe sequence jumps by increasing squares: h(k), h(k)+1, h(k)+4, h(k)+9… This breaks up the primary clusters that plague linear probing — at the cost of different problems.
introduction

Quadratic probing was developed as a direct fix for linear probing's clustering problem. By jumping further with each probe, elements that collide don't pile up in the same region. Two keys that hash to the same slot will still share the first probe position, but diverge quickly after that.

collision handling & secondary clustering

Primary clustering is solved — but quadratic probing introduces secondary clustering: any two keys that hash to the same initial slot follow the exact same probe sequence. They don't pile up as badly, but they still interfere with each other.

Critical constraint: table size must be prime. With a non-prime table size, the quadratic probe sequence may not visit all slots — you can fail to insert even when the table has empty slots. With a prime table size, the sequence is guaranteed to cover at least half the table.

Java Hashtable (old)

Academic / teaching
Quadratic probing is more commonly found in textbooks and teaching implementations than production code — it's the intermediate step between linear and double hashing.
things most people don't know

Quadratic probing is largely obsolete in practice. Double hashing (stage 5) solves secondary clustering too, with better distribution. Robin Hood hashing (stage 6) solves clustering differently and is strictly superior. Very few modern production systems use quadratic probing — it exists mainly as a teaching concept.

Stage 05 · Open addressing · Easy–Medium
Double hashing
Use two hash functions. When a collision occurs, the step size between probes is itself determined by a second hash of the key: h1(k) + i·h2(k). Two keys that collide at h1 now follow completely different probe sequences. Both clustering problems are solved.
introduction

Double hashing is the most theoretically sound open addressing scheme. The probe sequence is unique per key — two keys that hash to the same slot with h1 will almost certainly have different h2 values, so they diverge immediately. This gives distribution close to random probing.

collision handling

Probe sequence: slot = (h1(k) + i * h2(k)) % size. The key constraint: h2 must never return 0 (would cause infinite loop at the same slot), and gcd(h2(k), size) must equal 1 to guarantee the probe sequence visits all slots. The easiest way to ensure this: make table size prime and use h2(k) = prime - (k % prime) where prime is smaller than the table size.

operationaverageworst casenote

deleteO(1)O(n)still needs tombstones
spaceO(n)O(n)flat array, no pointers
who uses it & where
Python set (old)
CPython's set type historically used a double-hashing-like probe sequence to avoid clustering.
Cryptographic applications
Double hashing appears in digital signatures and proof-of-work systems (Bitcoin uses SHA256(SHA256(x))) — different context but same name.
things most people don't know

Double hashing is theoretically optimal among probing schemes — but Robin Hood hashing (stage 6) beats it in practice by reducing variance, not the average. The average probe count in double hashing and Robin Hood is similar; Robin Hood's maximum probe count is much lower.

Stage 06 · Advanced open addressing · Medium
Robin Hood hashing
Linear probing with one extra rule: when inserting, if the current element has probed further from its ideal slot than the incoming element, they swap. Rich elements yield to poor ones. This equalizes probe distances and gives dramatically better worst-case performance.
introduction

Invented by Pedro Celis in his 1986 PhD thesis at the University of Waterloo. The name comes from the idea of "stealing from the rich to give to the poor" — elements that are close to their ideal position yield their slot to elements that have traveled far.

The key metric is DIB (Distance from Initial Bucket) — how many probes an element is away from its ideal slot. During insert, if the incoming element's DIB > current element's DIB, swap them and continue inserting the displaced element.

collision handling & deletion

Insert works like linear probing but with swapping. The genius is in deletion: no tombstones needed. Instead, use backward shift deletion — when you delete an element, shift subsequent elements backward to fill the gap, stopping when you hit an empty slot or an element at its ideal position.

Why no tombstones? The Robin Hood invariant guarantees that elements are densely packed near their ideal position. Shifting backward restores this invariant without leaving ghost slots that accumulate over time.

spaceO(n)O(n)+1 integer per slot for DIB
who uses it & where
Rust HashMap (old)
Rust's standard HashMap used Robin Hood hashing until 2019, when it switched to SwissTable (hashbrown). Still one of the most famous Robin Hood implementations.
Abseil / SwissTable
Google's absl::flat_hash_map (used across Google's codebase) is inspired by Robin Hood principles combined with SIMD slot scanning.
Nginx
Nginx's internal hash tables use open addressing with Robin Hood-like properties for its configuration and routing tables.
ankerl::unordered_dense
A modern C++ Robin Hood hash map that consistently benchmarks faster than std::unordered_map and many alternatives.
things most people don't know

Early exit on lookup. During lookup, if the element you're examining has a lower DIB than the element you're searching for, the element you're searching for cannot exist — if it did, it would have displaced this element during insertion. You can stop probing early. This makes negative lookups faster.

Why Rust switched away. Robin Hood hashing has high insertion variance — some insertions are very fast, others are slow due to cascading swaps. SwissTable (SIMD-based) gives more predictable latency, which matters for Rust's use cases.

Stage 07 · Advanced open addressing · Medium
Cuckoo hashing
Two hash tables, two hash functions. Every key has exactly two candidate positions. Lookup always checks exactly two slots — O(1) worst case, not just average. When both positions are occupied, evict one element and rehome it, like a cuckoo bird pushing eggs out of a nest.
introduction

Invented by Rasmus Pagh and Flemming Friche Rodler in 2001. Named after the cuckoo bird which lays its eggs in other birds' nests, pushing the existing eggs out. The key guarantee no other hash table can match: lookup is always exactly 2 memory accesses, no matter how full the table is.

collision handling & cycle detection

On insert, check both positions. If either is empty, done. If both are occupied, evict one and try to rehome it in its alternate position. This can cascade. The danger: cycles. If the eviction chain loops back to a slot already visited, the insert has failed — trigger a rehash with new hash functions.

Cycle detection is mandatory. Without it, a failed insert loops forever. Track the number of evictions — if it exceeds a threshold (typically 2×table size), declare failure and rehash. This is the hardest part to implement correctly.

Real-world extension — cuckoo with a stash. Keep a small stash (typically 8 slots) for elements that fail to insert. This dramatically reduces the rehash rate while maintaining O(1) lookup (check table1, table2, then stash linearly).

who uses it & where
TikTok — Monolith
ByteDance's Monolith recommendation system paper (2022) uses a variant of cuckoo hashing for their real-time feature store. O(1) lookup is critical for serving recommendations at millisecond latency.
Network hardware
FPGA and ASIC network routers use cuckoo hashing for packet routing tables — O(1) worst-case lookup is a hard requirement at line speed (40Gbps+).

things most people don't know

Maximum load factor is ~50% per table. With two tables each at 50%, total space utilization is 50%. Compare to linear probing at 70%. Cuckoo hashing trades space efficiency for the O(1) worst-case lookup guarantee.

Cuckoo filters. A variant of Bloom filters built on cuckoo hashing — they support deletion (Bloom filters don't) and are more space-efficient. Used in networking for packet deduplication and flow tracking.

Stage 08 · Advanced open addressing · Medium–Hard
Hopscotch hashing
Each key must live within H slots of its ideal position — the neighborhood. A bitmap per slot tracks which nearby slots belong to its neighborhood. When the neighborhood fills up, swap elements around to restore the invariant. Designed for concurrent access.
introduction

Invented by Maurice Herlihy, Nir Shavit, and Moran Tzafrir in 2008. The goal was a hash table that works well with concurrent threads without requiring global locks. By bounding where an element can live (within H slots), any thread can check the entire neighborhood with at most H memory accesses — and H is typically 32 or 64, fitting in a CPU cache line.

collision handling

Each slot has a hop bitmap of H bits. Bit i being set means the slot i positions ahead contains an element that belongs in this neighborhood. On insert, find an empty slot using linear probing, then swap it backward into the neighborhood using the bitmap to track moves.

H is usually 32 or 64 — matching cache line size. All H positions of a neighborhood fit in one cache line, so checking an entire neighborhood is one cache access. This is the key performance insight.

operationaverageworst casenote

deleteO(1)O(H)update bitmap + remove element
spaceO(n)O(n)+H bits per slot for bitmap
who uses it & where
Intel TBB
Intel's Threading Building Blocks library includes a concurrent_hash_map based on hopscotch hashing — used in parallel computing workloads across Intel's software ecosystem.
High-frequency trading
HFT firms use hopscotch-inspired tables for order book lookups — bounded worst case and cache-line alignment are critical for microsecond latency.
things most people don't know

Hopscotch is the most concurrent-friendly hash table. Because each neighborhood fits in a cache line, threads can lock individual neighborhoods instead of the whole table. Multiple threads can insert and lookup simultaneously as long as they're in different neighborhoods.

Stage 09 · Distributed systems · Hard
Consistent hashing
Not a hash table for storing data — a routing algorithm for distributing data across machines. Keys and nodes both map onto a ring. A key belongs to the first node clockwise from it. Adding or removing a node remaps only 1/n of all keys instead of everything.
introduction

Invented by David Karger et al. at MIT in 1997. Before consistent hashing, distributed caches used node = hash(key) % num_nodes. When a node is added or removed, num_nodes changes, so almost every key remaps to a different node — catastrophic cache invalidation. Consistent hashing reduces remapping to just 1/n of keys.

how the ring works

Hash both keys and node names onto a circle (0 to 2³²). Each key is assigned to the first node clockwise from it. Add a node: only the keys between the new node and the previous node remapped. Remove a node: only its keys move to the next node clockwise.

Virtual nodes solve uneven distribution. With 3 physical nodes, the ring has 3 points and distribution is uneven. Map each physical node to 150 virtual nodes on the ring — distribution becomes uniform. This is how Cassandra and DynamoDB handle it.

who uses it & where
Amazon DynamoDB
The original DynamoDB paper (Dynamo, 2007) described consistent hashing as the core data distribution mechanism. Influenced an entire generation of distributed databases.
Apache Cassandra
Cassandra uses consistent hashing with virtual nodes (vnodes) for data distribution across its ring topology. The partition key is hashed to determine which node owns the data.
Discord
Discord uses consistent hashing to route WebSocket connections — when a server is added or removed, only a fraction of users reconnect instead of everyone.
Akamai CDN
Consistent hashing was originally developed for web caching at Akamai. It determines which edge server caches which content, minimizing cache misses when servers are added.
things most people don't know

Implement with std::map. The ring is just a sorted map from hash value to node name. std::map::lower_bound(hash(key)) finds the first node clockwise in O(log n). If it returns end(), wrap around to begin(). That's the entire routing algorithm.

Rendezvous hashing is an alternative. Instead of a ring, hash(key + node_name) for every node, pick the node with highest hash. Adding/removing a node still remaps only 1/n of keys, with no ring data structure needed. Simpler but O(n) lookup instead of O(log n).

Stage 10 · Probabilistic · Hard
Bloom filter
Not a hash map at all — a probabilistic membership data structure. Uses a bit array and k hash functions to answer "is this element in the set?" with zero false negatives and tunable false positives. Dramatically more space-efficient than a hash set.
introduction

Invented by Burton Howard Bloom in 1970. The insight: you don't always need to know exactly what's in a set — sometimes you just need to know if something is definitely not in it. A Bloom filter can tell you "definitely not in set" or "probably in set" using a fraction of the memory a hash set would require.

how it works

A bit array of m bits, all initialized to 0. k independent hash functions. To insert: hash the element with all k functions, set those k bits to 1. To query: hash with all k functions, check those k bits — if any is 0, definitely not in set. If all are 1, probably in set (could be false positive).

No deletion. You can't unset a bit — other elements may have set it. Counting Bloom filters use counters instead of bits to support deletion, at higher memory cost.

Optimal k formula: k = (m/n) × ln2 where m = bit array size, n = expected elements. This minimizes false positive rate for given memory.

time & space complexity
operationcomplexitynote

who uses it & where
Google Bigtable / LevelDB
Uses Bloom filters per SSTable to avoid disk reads for keys that don't exist. Without it, every negative lookup requires reading from disk. With it, 99%+ of negative lookups are answered from memory.
Cassandra
Every SSTable has a Bloom filter. Before reading from disk, check the filter — if it says "definitely not here", skip the disk read entirely. Reduces disk I/O by orders of magnitude.
Chrome browser
Uses a Bloom filter for Safe Browsing — checks if a URL is in the malicious URL list locally before querying Google's servers. Protects privacy and reduces latency.
Bitcoin
SPV (light) nodes use Bloom filters to tell full nodes which transactions they care about, without revealing their exact addresses. BIP 37.
things most people don't know

1% false positive rate costs only ~10 bits per element. A hash set storing a 64-bit key uses 64 bits per element. A Bloom filter achieving 1% false positives uses ~10 bits per element — 6× more space-efficient. At 0.1% false positives it's still only ~15 bits.

Cuckoo filters are often better. Cuckoo filters (2014) achieve similar false positive rates with less space, support deletion, and have better cache performance. Bloom filters are older and more widely known, but cuckoo filters are technically superior for most use cases.

Stage 11 · Probabilistic · Hard
Count-Min sketch
A probabilistic frequency counter. Uses a d×w matrix of counters and d hash functions to estimate how many times any element has appeared in a stream. Never undercounts. May overcount, but the error is bounded by ε with probability 1−δ.
introduction

Invented by Graham Cormode and S. Muthukrishnan in 2003. The problem it solves: you have a stream of billions of events and want to know the frequency of any element — but you can't store every element. A hash map would run out of memory. A Count-Min sketch answers frequency queries in O(1) using constant memory, with a provable error bound.

how it works

d arrays, each of width w. d independent hash functions, one per array. On update(x, count): for each of d arrays, increment position h_i(x) by count. On query(x): return the minimum across all d arrays at position h_i(x).

Why minimum? Collisions only ever add to a counter (never subtract), so every counter is an overestimate. The minimum across d independent arrays gives the tightest overestimate — the array least affected by collisions.

Choose d and w from ε and δ: w = ceil(e/ε), d = ceil(ln(1/δ)). For 1% error (ε=0.01) with 99% confidence (δ=0.01): w=272, d=5. That's 1360 counters total — tiny for frequency estimation over billions of events.

who uses it & where
Twitter / X
Uses Count-Min sketch to track trending topics in real-time. Counting exact frequencies of billions of tweets per day would be impossible — the sketch approximates it in constant memory.
Apache Flink / Spark
Both streaming frameworks include Count-Min sketch as a built-in operator for approximate frequency queries over infinite streams.
Cloudflare
Uses Count-Min sketch for DDoS detection — tracking request frequencies per IP at line rate without storing every IP address.
Redis (4.0+)
Redis's top-k data structure uses Count-Min sketch internally to track the most frequent elements in a stream without storing all elements.
things most people don't know

Count-Min sketch never undercounts. Because collisions only add to counters, the estimate is always ≥ true frequency. This one-sided error is useful — you can safely use it as a conservative lower bound. Bloom filters have a similar one-sided property (no false negatives).

Heavy hitters algorithm. Combine Count-Min sketch with a small heap to find the top-k most frequent elements. Query the sketch for each candidate in the heap — O(k log k + d) to find top-k over a billion-element stream. This is how Twitter finds trending topics.
